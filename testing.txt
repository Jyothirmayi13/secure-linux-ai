------------------------------------------------------------
  PHASE 3 — MCP GATEWAY FACADE (added 2026-10-16)
------------------------------------------------------------

Zero new dependencies. The official `mcp` SDK is absent from both venvs and its
dep tree (uvicorn, starlette, sse-starlette, httpx, jsonschema) is the wrong
thing to put inside a security boundary, so the stdio transport — newline-
delimited JSON-RPC 2.0 — is implemented directly in mcp_server.py.

Design rule being tested: the CLI and the MCP server call the SAME decision
core (gateway.py) and the SAME tool registry (tools.py). A boundary that exists
twelve times can be bypassed, so duplication is treated as a bug, not as
belt-and-braces.

T35: CLI and MCP share one decision core
  - main.decide_command / main.decide_tool_call / main.call_capability are the
    gateway.py objects, and so are mcp_server's; neither front-end re-bound the
    name, which would mean a private copy of the boundary
  - AST check on gateway.py: no print(), no exit(), no `import sys` — a security
    core that terminates the process cannot be embedded by a front-end
  - Three bypass attempts through the shared path (/etc/shadow read, full-
    filesystem find, limit=99) all blocked
  - Result: PASS

T36: Two planes, and neither of them executes
  - TOOL_NAMES == CAPABILITY_TOOLS == names in TOOL_SPECS (registry, schemas and
    functions cannot drift apart)
  - advertised MCP surface == capability(5) + control(4) == 9 tools, and every
    advertised name is known to the classifier — an unclassified tool would be
    checked by nothing
  - no advertised name contains exec/run/shell/write/delete/remove/apply/sudo/
    install/kill: the server has no execution tool at all. An agent cannot ask
    for one because it is not a matter of policy, it is not a tool.
  - Result: PASS

T37: MCP handshake, capabilities, notifications
  - initialize echoes 2025-06-18, advertises {tools:{listChanged:false}},
    returns serverInfo and the "no tool that executes" instruction
  - a client offering 1999-01-01 is answered with our own version rather than
    silently mis-negotiating
  - notifications/initialized, notifications/cancelled and a notification-shaped
    tools/list all produce NO response (the spec forbids one)
  - ping answers {}; jsonrpc:"1.0" and a request with no method -> -32600
  - clientInfo.name is carried into the audit subject ("via qoder-agent")
  - Result: PASS

T38: Allowed MCP read executes and is logged
  - get_system_status over the protocol returns data; the audit row is status
    "executed", rule baseline.tool_allow_list, and the reason says explicitly
    "Executed under policy without human confirmation (agent-initiated through
    MCP)". Agent-initiated reads are never recorded as if a human confirmed them.
  - Result: PASS

T39: MCP refusals name the rule and are signed
  - search_text_file path=/etc/shadow -> isError, "REFUSED by the security
    gateway ... [rule floor.deny_path:/etc/shadow]"
  - the refusal is a signed audit row carrying rule_id and the argument JSON;
    chain_ok + signed_ok + 0 unsigned, and an exported report of just that
    refusal verifies fully_signed offline
  - Result: PASS

T40: Control-plane calls are policed like diagnostics
  - evidence_verify(path=/etc/shadow) -> floor.deny_path (the same argument-
    VALUE check the capability tools get; a question tool is not a bypass)
  - evidence_verify(path=/usr/share/nginx/x.json) -> policy.read_roots
  - policy_decide with an undeclared "shell" argument -> baseline.tool_arguments
  - evidence_report hours=0 -> baseline.tool_limit; policy_show with a list
    instead of an object -> baseline.tool_arguments
  - policy_decide "rm -rf /" answers allowed:false and states nothing executed;
    5 blocked rows recorded, one per attempt
  - Result: PASS

T41: Unknown tool/method, probed name logged
  - tools/call name=delete_files -> -32602 invalid params, no crash, AND a

T42: stdio framing; malformed line; pure stdout

    oversight - but it means "approvals stop an agent from running something"

    Phase 4b replaced its confirm/execute block with the approval lifecycle
    (T58 covers that path with the CLI functions directly, and the strict-mode

    by that host cannot be attributed to a specific person beyond the OS
    username the gateway saw. Per-user keys are the missing piece.
  - The token is bound to a subject hash, not to the process that runs it. A
    human-approved command that then execs something else (a script that calls
    rm) is only stopped by the risk engine's own reading of those bytes at mint

    redeemers have not been tested under real contention; T55/T56 exercise
    sequential replay, not a race.
  - Expiry depends on the host clock. A machine that jumps its clock backwards
    could make an expired token live again; there is no monotonic-clock or
    server-time source.

  RETRACTION: --reset-key DOES NOT ROTATE THE HOST KEY (2026-10-20)
================================================================================

  WHAT WAS WRONGLY CLAIMED. docs/quickstart.md's Reset section said
  `ssm --reset-key` gives you "new host identity: rows from the old key stop
  verifying", and its troubleshooting section pointed at `--reset-key` for a
  half-written identity directory. Writing docs/runbook.md this evening meant
  reading the option's implementation, and it does neither:

    env_path = Path(__file__).resolve().parent / ".env"
    if env_path.exists(): env_path.unlink()  -> ".env has been deleted."

  That is the MODEL API KEY. It never opens the identity directory, never
  touches audit.sqlite3, and prints nothing about host signing. The comment in
  the code is even correct ("Handle API key reset if requested") - the docs were
  the ones that lied, and they had been sitting there since the quickstart was
  written. No test covered it, because a test written from the same wrong
  assumption would have asserted the wrong thing.

  WHAT IS TRUE INSTEAD
  - There is no host-key rotation command. The way to change the signing key is
    to delete the identity directory whose path `ssm --evidence-show` prints;
    `load_or_create_identity()` makes a new pair on the next run.
  - Consequence, stated: rows already stored were signed by the key that is gone,
    so they stop verifying as this host's. Reports exported *before* the
    rotation keep verifying, because each report carries its own public key. So
    export evidence before rotating, and date the rotation in the next report's
    `--note`, which is inside the signed core.
  - `--reset-key`'s real behaviour is now documented in both files, including
    what happens after it: nothing is prompted for on the next run, and with no
    key in the environment the gateway refuses to choose a cloud provider.

  ALSO FIXED IN THE SAME PASS, from reading the code rather than the prose:
  the runbook quotes `--evidence-show`'s actual output ("Chain OK - N rows
  recompute cleanly; M signed.", "Chain BROKEN" plus each failure, and the
  "N row(s) predate host signing" line) instead of inventing labels; the
